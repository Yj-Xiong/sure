在仓库根目录执行下面的脚本。它读取示例任务清单、锁定的 engine capability 和 runtime，输出一个真实的 objective_metric_plan.json。

./sure/skills/sure_audio_eval/examples/run-example.sh

输出位置 .sure/examples/audio-eval-plan/objective_metric_plan.json

真实任务的完整入口

提供任务清单、主观原始提交和客观输入后，使用同一条命令推进完整状态机。

/sure_audio_eval task_manifest=tasks/example/task_manifest.json \
  subjective_source=ratings/example/*.csv \
  objective_source=objective/example/*.jsonl \
  objective_metrics=pesq,dnsmos \
  analysis_unit=model_condition \
  output_dir=runs/example/audio-eval-001

从输入到产物

每一步完成后才允许进入下一步。

01
resolve_task读取 task version、dataset version、sample IDs、candidate keys、analysis candidate keys、scale、audio version 和 interface contract，写入 task_manifest_resolved.json。
02
resolve_metrics从锁定 capability manifest 找到 pesq 和 dnsmos route，核对方向、类型、reference mode 和 pipeline，写入 objective_metric_plan.json。
03
validate_audio为每个模型条件检查音频可解码性、采样率、声道、时长、版本、响度、True Peak 和 SHA-256，写入 audio_manifest.json。
04
run_objective使用锁定 engine 执行 intrusive 和 non-intrusive route，输出逐条件 objective rows、route plan 和 engine provenance。
05
ingest_subjective 到 render_report保留原始评分，完成最新有效去重、完整组、MOS、SD、t-CI95、主观筛查、模型条件 Pearson / Spearman，最后写出独立 HTML 和 final manifest。
示例和正式运行的关系

示例脚本实际生成指标计划。完整入口只有在提供真实音频、客观输入和主观提交文件后才会生成正式运行产物。

核心分析规则

先明确比较对象，再计算主观分数和客观指标之间的关系。

主相关性单位

一个条件点等于一个 sample_id 与 model_candidate 的组合。先对听评者原始分求 MOS，再与相同条件的客观指标配对。

  • 每个已确定指标分别计算 Pearson 和 Spearman。
  • 输出共同条件点数 n 和实际参与分析的模型数 model_count。
  • model_count 按当前指标实际配对的模型候选去重计算，缺少完整主客观条件点的模型不会计入。
  • 保留指标类型、方向、reference mode、pipeline 和 engine provenance。

模型条件点状态

指标模型条件点数量实际模型数状态来源
metric planmissingmissingblocked未绑定正式 objective rows 和 condition summary
per metricmissingmissingblocked正式运行后从 CSV 与分析表读取

筛查依据

筛查只读取模型候选的主观评分分布。它不读取客观分数、回归残差或相关系数，也不因为相关性变化自动删除记录。

筛查产物

筛查前后结果同时保存，并写入 flagged list 和 rule version。高杠杆点只作为诊断信息，不能直接改变分析样本。

模型候选集合

analysis_candidate_keys 在任务冻结时由用户决定。每个指标只统计实际存在完整 MOS 和 objective 配对的模型。

放行条件

analysis report 的指标集合必须与 objective metric plan 完全一致，模型候选必须与 task manifest 一致，所有条件点必须能追溯到音频版本和 SHA-256。

与主观评测接口对齐

平台侧的发起、采样、评分和交付设置，在任务冻结时写入接口契约。

榜单和任务发起

  • 可以关联已有榜单，也可以创建新的榜单。
  • 结果在结算后发布，发起人的备注和评分人的说明分别控制可见范围。
  • 评测类型先写入任务，当前覆盖语音增强和 TTS 扩展入口。

样本和模型对象

  • 样本来源明确为平台数据集或上传包，抽样策略随任务冻结。
  • 每个样本保留干净音频、带噪音频和处理后音频的对应关系。
  • 模型候选写入白名单，允许删除或追加模型由任务契约声明。

指标和评分规则

  • 每个指标声明名称、分值范围、步长、评分规则和提示语。
  • 参考音频说明可以对评分人隐藏，但参考角色和校验规则仍在产物中保留。
  • 当前任务按一次完整提交聚合算术平均，后续统计扩展仍从原始分计算。

评分过程和交付

  • 评分开始前记录设备选择，页面兼容移动端入口。
  • 评分中断后可以继续，发起人可以暂停、取消或重新发起。
  • 分享入口只负责进入任务，最终榜单展示经过结算的结果。
契约落点

interface_contract 随 task_manifest_resolved.json 冻结，后续的 objective metric plan、subjective ingest 和 HTML report 都读取同一份配置。

执行规范

每一步都有明确的输入、检查和放行条件。

任务先锁定

先确定本次评测到底比较什么。

  • 冻结任务版本、数据版本、音频版本和样本清单。
  • 冻结参与主相关性的 analysis_candidate_keys。
  • 明确模型、隐藏参考和未处理输入的角色。
  • 固定评分量表和评分步长。

指标先确定

没有指标计划，不开始客观评分。

  • 逐项写明指标类型和方向。
  • 明确是否需要同一样本的参考音频。
  • 使用任务阶段已冻结的模型候选，只锁定指标和执行 route。

音频先核验

先证明输入音频就是任务要求的音频。

  • 检查文件能否解码、采样率、声道和时长。
  • 检查音频版本和文件 SHA-256。
  • 记录响度处理和 True Peak 信息。

原始评分不覆盖

原始提交保留，整理结果另写文件。

  • 每条评分带有听评者、会话、设备、批次和时间。
  • 相同任务、听评者、样本和候选只保留最新有效记录。
  • 无效行保留拒绝原因。

完整组才聚合

缺一项候选，就不把这一组送入主分析。

  • 完整听评组才计算 MOS。
  • 每个样本和候选输出人数、MOS、SD 和 t-CI95。
  • 人数少于 2 时不估计 CI95。

只分析模型条件

相关性回答模型方法与主观感受是否一致。

  • 分析单位是 sample 和 model candidate。
  • 只使用任务冻结的 analysis_candidate_keys。
  • 隐藏参考和未处理输入留在记录中，但不进入相关性。
  • 每个指标分别输出 Pearson 和 Spearman。

筛查只看主观分

筛查不能被客观分数或相关性结果影响。

  • 只根据模型候选的主观评分分布标记异常。
  • 最低评分人数默认按任务选定的分析模型数量确定，也可由 screening_policy.min_ratings 明确设置。另要求 IQR 大于 0、超出 3×IQR 且偏离中位数至少 20 分。
  • 保留筛查前、筛查后和 flagged list。
  • 高杠杆点只做诊断，不因相关性变化自动删除。

失败停在当前阶段

发现问题就留下诊断，修复后从 checkpoint 继续。

  • 不使用旧版本结果补齐当前运行。
  • 不静默更换指标、模型、engine 或数据版本。
  • 重复无进展动作由 loop guard 停止。
