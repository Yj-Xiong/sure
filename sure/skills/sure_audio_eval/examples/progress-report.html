执行流程

先锁定任务和指标，再检查音频、评分和分析结果。

01resolve_task冻结任务、版本、候选角色和量表
02resolve_metrics锁定指标类型、方向和 route
03validate_audio检查可解码、条件和 SHA-256
04run_objective执行或严格适配客观结果
05ingest_subjective保留原始分并做最新有效去重
06aggregate_subjective生成 MOS、SD、t-CI95
07joint_analysis输出模型条件 Pearson / Spearman
08render_report生成 HTML、final manifest 和 run report

核心分析规则

先明确比较对象，再计算主观分数和客观指标之间的关系。

主相关性单位

一个条件点等于一个 sample_id × model_candidate。先对听评者原始分求 MOS，再与相同条件的客观指标配对。

  • 每个已确定指标分别计算 Pearson 和 Spearman。
  • 输出共同条件点数 n 和模型数 model_count。
  • 保留指标类型、方向、reference mode、pipeline 和 engine provenance。

与主观评测接口对齐

平台侧的发起、采样、评分和交付设置，在任务冻结时写入接口契约。

榜单和任务发起

  • 可以关联已有榜单，也可以创建新的榜单。
  • 结果在结算后发布，发起人的备注和评分人的说明分别控制可见范围。
  • 评测类型先写入任务，当前覆盖语音增强和 TTS 扩展入口。

样本和模型对象

  • 样本来源明确为平台数据集或上传包，抽样策略随任务冻结。
  • 每个样本保留干净音频、带噪音频和处理后音频的对应关系。
  • 模型候选写入白名单，允许删除或追加模型由任务契约声明。

指标和评分规则

  • 每个指标声明名称、分值范围、步长、评分规则和提示语。
  • 参考音频说明可以对评分人隐藏，但参考角色和校验规则仍在产物中保留。
  • 当前任务按一次完整提交聚合算术平均，后续统计扩展仍从原始分计算。

评分过程和交付

  • 评分开始前记录设备选择，页面兼容移动端入口。
  • 评分中断后可以继续，发起人可以暂停、取消或重新发起。
  • 分享入口只负责进入任务，最终榜单展示经过结算的结果。
契约落点

interface_contract 随 task_manifest_resolved.json 冻结，后续的 objective metric plan、subjective ingest 和 HTML report 都读取同一份配置。

执行规范

每一步都有明确的输入、检查和放行条件。

任务先锁定

先确定本次评测到底比较什么。

  • 冻结任务版本、数据版本、音频版本和样本清单。
  • 明确模型、隐藏参考和未处理输入的角色。
  • 固定评分量表和评分步长。

指标先确定

没有指标计划，不开始客观评分。

  • 逐项写明指标类型和方向。
  • 明确是否需要同一样本的参考音频。
  • 只使用当前锁定 engine 支持的 route。

音频先核验

先证明输入音频就是任务要求的音频。

  • 检查文件能否解码、采样率、声道和时长。
  • 检查音频版本和文件 SHA-256。
  • 记录响度处理和 True Peak 信息。

原始评分不覆盖

原始提交保留，整理结果另写文件。

  • 每条评分带有听评者、会话、设备、批次和时间。
  • 相同任务、听评者、样本和候选只保留最新有效记录。
  • 无效行保留拒绝原因。

完整组才聚合

缺一项候选，就不把这一组送入主分析。

  • 完整听评组才计算 MOS。
  • 每个样本和候选输出人数、MOS、SD 和 t-CI95。
  • 人数少于 2 时不估计 CI95。

只分析模型条件

相关性回答模型方法与主观感受是否一致。

  • 分析单位是 sample 和 model candidate。
  • 隐藏参考和未处理输入留在记录中，但不进入相关性。
  • 每个指标分别输出 Pearson 和 Spearman。

筛查只看主观分

筛查不能被客观分数或相关性结果影响。

  • 只根据主观评分分布标记异常。
  • 不因为相关性变高而删除评分。
  • 保留筛查前和筛查后结果。

失败停在当前阶段

发现问题就留下诊断，修复后从 checkpoint 继续。

  • 不使用旧版本结果补齐当前运行。
  • 不静默更换指标、模型、engine 或数据版本。
  • 重复无进展动作由 loop guard 停止。

标准按阶段使用

引用用于界定工作边界。

  • 任务与评分对象 BS.1284-2、P.808。
  • 音频条件 BS.1770。
  • MOS、CI95 和相关性 P.1401、NIST Statistical Handbook。
  • 筛查和报告组织 ETSI TS 103 281 V1.3.1。

结果如何留下

每个阶段单独留下结果，下一步只读取已经检查过的内容。

  • evaluation_context.json任务、输入源、指标、标准和 capability 身份的冻结快照
  • tool_registry.json注册脚本、阶段归属、输入和输出契约
  • task_manifest_resolved.jsontask/version/sample/candidate/role/scale/audio policy
  • objective_metric_plan.jsonmetric type、direction、reference mode、pipeline 和 standards
  • audio_manifest.json路径、格式、采样率、声道、时长、响度、True Peak 和 SHA-256
  • objective_run_report.json逐条件客观分、engine route、pipeline 和失败诊断
  • subjective_ingest_report.json原始来源 hash、最新有效去重、拒绝行和完整组
  • condition_summary.jsonsample × candidate 的 MOS、SD、t-CI95 和缺失情况
  • analysis_report.jsonmodel-condition correlation、screening before/after 和 provenance
  • analysis.html / final_manifest.json / main_agent_run_report.json独立报告、内容寻址清单和运行终态
